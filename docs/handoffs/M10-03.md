# M10-03 — owner runbook: capture the Lab fixture corpus

Ten to fifteen minutes at the machine with the game installed. Repeat on the
second OS when convenient; the first platform unblocks the parsers.

## Before capturing

1. Log a character in on each installed flavor (retail; the Forever beta if
   installed), with at least three or four addons enabled. Open the keybind
   and macro panels and change one of each so the cache files are fresh.
2. Combat log. The log records every unit near you, not just you, and the
   tool refuses a log that names any other player (unless you ask it to
   pseudonymise them; see `--pseudonymise-other-players` under "Capture").
   Go somewhere you are
   alone in an instance: on retail walk into a legacy raid or old dungeon
   solo; on Forever a low-level dungeon. Type `/combatlog` just before the
   first boss, kill it, type `/combatlog` again. A boss pull is what writes
   `COMBATANT_INFO`; a training dummy never does (reviewer memory,
   **[verify]** here). Before `/combatlog`, turn on Advanced Combat Logging
   (System → Network, location **[verify]**; community documentation says
   `COMBATANT_INFO` and the advanced per-event fields are only written with
   it on; the CVar is reported as `advancedCombatLogging` **[verify]**).
   Record in the findings whether the header line shows
   `ADVANCED_LOG_ENABLED,1`. Dismiss any pet or summoned demon before
   `/combatlog`.
   The log is mostly public game text (creature, spell and NPC names), so
   the tool rewrites your names only in the quoted unit name straight after
   one of your own GUIDs, and refuses the whole log if one of your names
   appears anywhere else (a pet's name, a boss or spell that happens to share
   a name with you). Pass `--own-guid` (step 6) for the character you log
   with; on the Forever beta no config file records your GUID, so there
   it is required. If the log is still
   `REFUSED` with "unmapped player GUID", someone was in range: redo it, do
   not edit the log. If you cannot redo it (the only log you have names
   other players), add `--pseudonymise-other-players` instead: see
   "Capture" below. The tool keeps the first 2 000 lines of the *newest*
   `WoWCombatLog*` file, or of each file you name with `--combat-log`
   (see "Capture"). If your client appends to one file across sessions
   rather than starting a new timestamped one (**[verify]**, and record
   which), the head of that file is your *oldest* session, not the boss
   pull: check that the first timestamp in the captured log is from this
   step, and if not, move older logs out of `Logs/` before repeating it. Note in `docs/DATA_SOURCES.md` if the instance log looks thinner
   than expected (12.x restricted logging), and whether Forever wrote one at
   all. `COMBATANT_INFO` lists your exact gear and talents; decide whether
   you are comfortable with that being public before committing.
   The tool moves every timestamp in the log, and the date and time in its
   file name, by a secret offset drawn for that log alone (60 to 400 days
   either way; it is never shown). Creature and object GUIDs get invented
   server, zone and spawn numbers. What this hides is the time of day and the
   exact date of your session. The date is still bounded: it falls inside
   the live window of the client build, which is in the provenance row and
   the log's header, and before the date of the commit. The `-4`-style
   suffix is kept as written, so it shows whether you played in
   daylight-saving time. What stays real is every health, position, damage,
   healing and gear value. Those are the same in any other group member's
   log of the same fight, so someone who holds such a log can still match it
   to yours. A solo log has nothing to match against; a group log stays
   linkable that way.
   **A log whose unshifted copy was ever published** (committed, pushed,
   pasted) tells anyone who compares the two copies its own offset. Never
   re-capture such a log expecting its time to be hidden; record a new one.
   Other logs are not affected, because each log has its own offset.
3. Log out to the character screen (this writes SavedVariables), then exit
   the game. The tool will run with the client open, but the files on disk
   are stale until logout, so close it first.
4. Optional, once per flavor: launch with `-console`, open the console at
   the login screen with the backtick key, run `ExportInterfaceFiles code`
   (flag, key and command from memory, **[verify]**).
   Not captured as a fixture (it is Blizzard's source), but later waves
   read it locally, and its presence exercises `layout`.
5. Collect the strings the tool cannot discover; each goes in as
   `--extra-name "<text>"`: guild and community names, the name part of your
   BattleTag, your real first and last name, your OS username, hunter or
   warlock pet names, old character names from renames or transfers
   (those leave folders behind), and the author name or handle in
   `## Author:` of any addon you wrote.
6. For each alt that tracker addons know about, run
   `/dump UnitGUID("player")` on it and pass the value as `--own-guid`. A
   refusal never prints the GUID, so you cannot read it off the output.

The tool finds character and realm names from the folders under
`WTF/Account/` of every flavor folder in the install, including leftovers
from uninstalled products. It cannot know anybody else's name.

## Capture

```bash
cd ~/path/to/wowlab
git checkout -b m10/03-lab-corpus origin/main
make setup

# macOS
uv run python scripts/lab_capture.py \
  --root "/Applications/World of Warcraft" \
  --out lab/core/tests/fixtures/incoming --dry-run
# Windows (PowerShell)
uv run python scripts/lab_capture.py `
  --root "C:\Program Files (x86)\World of Warcraft" `
  --out lab/core/tests/fixtures/incoming --dry-run
```

`--root` is wherever the install actually lives. Read the dry-run plan, then
run again without `--dry-run`, adding:

- `--kind <folder>=retail --kind <folder>=forever`, with the flavor folder
  names exactly as they appear as the first path segment of the dry run's
  `would write` lines (do not type them from memory;
  the Forever folder name is one of the things this ticket records). Two
  flavors cannot share a kind.
- every `--extra-name` and `--own-guid` from steps 5 and 6, including
  `--own-guid` for the character you logged the combat log with (always on
  the Forever beta): the tool rewrites your name in the log only after a
  GUID it knows is yours, and refuses the log rather than guess.
- `--pseudonymise-other-players`, only if your combat log names other
  players and you will not record another one. It touches the combat log
  and nothing else. Each other player gets an invented GUID
  (`Player-9998-00000001`, `-00000002`, … in the order they first appear)
  and an invented name (`Labothera`, `Labotherb`, …), the same everywhere in
  the log and in every log of that run. Only the name inside the quotes right
  after their GUID is changed; the flag numbers after it stay. If their unit
  name has a realm part that is one of your realms, it is scrubbed like your
  own realm; a realm the tool does not know becomes `Labotherrealma`, …; a
  region such as `US` stays. The log is still refused if one of their real
  names (or an unknown realm from their unit name) appears anywhere else in
  it, for example in an emote, a spell or aura name, or their pet's name,
  because text there cannot be rewritten safely. Their name is found in any
  casing, with accents added or dropped (`Zoe` finds `Zoë` and the other way
  round), in full-width letters, with invisible characters such as a
  zero-width space or soft hyphen inside it, and with any run of blanks,
  apostrophes or dashes (typographic ones included) between its letters. A
  realm the tool does not know is also found spaced or split (`Gloam Spire`
  for `GloamSpire`). It is refused as well if
  their name is a word the log itself uses (such as `Nil`, `True`,
  `Default`, `Neutral`), because the tool cannot tell that word apart from
  the log's own text, and if one of their GUIDs never once appears next to
  their name anywhere in the kept lines (a GUID that only ever shows up
  alone, for example only in `COMBATANT_INFO`). Keep passing `--own-guid` for your own character: without it you
  are treated as another player (your name is still replaced, but as
  `Labother…`, so the fixture no longer says which unit is you).
- `--combat-log <file name>`, once per log you want. Without it the tool
  captures only the newest log. With it, the tool captures **only the logs you
  name**: the newest is dropped unless you name it too. To capture two logs,
  name both, for example
  `--combat-log WoWCombatLog-010126_120000.txt --combat-log WoWCombatLog-010226_120000.txt`
  (placeholders: use your real file names from `Logs/`). Do not re-capture a
  log whose unshifted copy was ever published in the hope of hiding its time;
  record a new log instead. If such a log must be captured at all, capture it
  in a run of its own, and treat its time as public anyway. Give each name exactly as it
  appears in `Logs/`, with no folder. It must be `WoWCombatLog.txt` or
  `WoWCombatLog-MMDDYY_HHMMSS.txt`, in that case. A name the tool cannot find
  in the `Logs/` of any captured flavor, or of any other shape (a `.gz` copy,
  a renamed log), stops the run before anything is written. The message
  names it by position ("the 2nd --combat-log"), never by name, because a log
  name holds the real date and time. Each named log is checked, written and given a
  provenance row on its own, with the same `--log-lines`, `--own-guid` and
  `--pseudonymise-other-players` rules. Its output file carries the shifted
  date in its name, not the one you typed. Another player keeps one invented
  name in every log of the run, and two players never share one. A log that
  is compressed, holds a NUL byte or is not UTF-8 text is refused.
- `--platform macos|windows` only if the files were last written by a client
  on a different OS from this machine (Wine, a mounted drive). Off macOS and
  Windows the tool insists on it.

`<out>/<platform>` (for you: `lab/core/tests/fixtures/incoming/macos/` or
`…/windows/`) must be empty; another platform's folder beside it is fine.
The tool never deletes, so it refuses to start over a staging folder that
already holds files; clear that folder by hand between runs. With `--reuse-out`
it runs anyway, lists every file it did **not** write this time and exits
non-zero: those are stale copies from an earlier, less-scrubbed run, and
they must be deleted before anything is moved.

The real names are never printed. `--show-map` prints the name → pseudonym
map for your eyes only; never paste that output anywhere. With `--show-map`
on, an exit-2 message about a name that is too short (one character) or
equal to a format keyword (`set`, `bind`, `end`, `ver`, `true`, `false`,
`nil`, `player`) also prints that name; without it the message says only
`a character name (3 characters)`. The same holds for two more exit-2
messages: a realm or character folder name with no letters in it
(`… has no letters, so it cannot be told apart from an ordinary number`),
and an `--extra-name` that is a word the client itself writes, such as
`GUILD` or `PARTY` (`--extra-name: a value (N characters) is a word the
client writes itself`). Fix the `--extra-name` and re-run rather than
pasting the message.

## Reading the output

0. If the tool stops with exit 2 and "a folder … could not be listed" or "a
   Config.wtf or config-cache.wtf could not be read": nothing was captured,
   on purpose, because the identity map would have been incomplete. Close
   the game if it is running (**[verify]** whether a running Windows client
   blocks reads of these files at all), give your terminal access to
   the install folder (macOS: Privacy → Files and Folders / Full Disk
   Access) and re-run. Do not work around it by copying files elsewhere.
1. Read the `identity map:` line (the second line):
   `identity map: N names (A accounts, R realms, C characters, E extra), G own GUIDs, K CVars blanked`.
   A, R, C and E count distinct *names*, not folders: a character name you
   use on two realms counts once, and a name that is also a realm's (or an
   `--extra-name` equal to a folder name) is absorbed by the first category.
   Allow for that, then check R covers every realm folder under any
   `WTF/Account/`, old flavors included, and that nothing you passed is
   missing. On the Forever beta the folder tree is
   `WTF/Account/<ACCOUNT>/<digits>/<First>-<Second>/`: the digits folder is
   the realm's numeric id and is not counted; a Forever character's second
   name (the part after the hyphen) is counted under R, because the tool
   scrubs it the same way as a realm name, so R is your real realms plus
   your distinct second names. Its pseudonym reads `Labrealm…` for the same
   reason; in the corpus, `Labcharb-Labrealmd` is a first and second name,
   not a character and a realm. The digits
   folder shows as `1`, `2`, … in output paths. G is the number of your GUIDs the tool found: `lastCharacterGuid`
   from each config file (which files carry it is one of the **[verify]**
   findings), your own characters named in a combat log, and `--own-guid`.
   If G is 0, every file holding a GUID of yours will be refused: pass
   `--own-guid`. On the Forever beta G is always 0 (no `lastCharacterGuid`
   in any config file), so `--own-guid` is mandatory for the SavedVariables
   and combat-log stages. K is the length of the deny-list (eight plus every
   `--blank-cvar`), not a count of lines changed; per-file counts are the
   `cvars-blanked: n` cell.
2. `REFUSED` lines, and the "candidates passed over" list: nothing was
   written for that file, which is the safe outcome. Most lines give a byte
   offset and a line number, never the text. The longer-word, third-party
   addon file and addon-name labels below give a count only, because the
   match sits in a public name, and its position alone would give it away. Never edit an output file to
   make it pass, and never hand-copy a refused file into the corpus. By
   label:
   - `unmapped player GUID`: yours on an alt (pass `--own-guid`), or someone
     else's (choose a different file with `--sv`, or redo the log alone; for
     a combat log you cannot redo, add `--pseudonymise-other-players`).
   - `other player's name outside a unit field xN` (combat log, with
     `--pseudonymise-other-players` only): the real name of another player in
     the log, or a realm from their unit name that is not yours, also appears
     N times somewhere other than their unit names: an emote, a spell or
     aura name, a pet named after them. A name of five letters or more counts
     even inside a longer word, and with any run of blanks, apostrophes,
     dashes or underscores between its letters; a shorter one only as a whole
     word. Any casing counts, with accents added or dropped, in full-width
     letters, or with invisible characters inside. Only the count is printed.
     The log cannot be used; there is no override.
   - `surviving identity string (folded or separated spelling) xN` (any
     file): one of your own names is still in the file in a spelling the
     rewrite does not touch. It may be in full-width letters, have an accent
     added or dropped, have an invisible character inside, or have a tab,
     no-break space, typographic dash or doubled space where the name has a
     space. Only the count is printed. Swap the file, or for a combat log
     record another.
   - combat-log timestamp refusals (count only): `combat-log line without a
     recognised timestamp`, `combat-log timestamp that cannot be shifted` (a
     date that does not exist), `date or time inside a combat-log record`,
     and `combat-log UTC-offset suffix that changes within the log` (for
     example a log that crosses a daylight-saving change). The tool will not
     keep a real date or time it cannot move. Report the label and count; do
     not edit the log.
   - `combat-log timestamp in a shape not verified on real logs` (count
     only): the log writes its timestamps in a shape other than the one
     verified on 2026-09-24 against your real logs (count-only check: the
     hour is always two digits, the month is unpadded, the year has four
     digits). The likeliest cause is a zero-padded day (`9/05`): day padding
     is unverified, because no real log had a day below 10. **Report this
     label and count**: it settles that open question.
   - `combat log starts with a compressed-file signature`, `combat log holds
     a NUL byte`, `combat log is not valid UTF-8`: the file is not a plain
     text log, and nothing in it was scrubbed.
   - `other player's name cannot be checked xN` (combat log, with
     `--pseudonymise-other-players` only): N parts of other players' unit
     names are words the log or the tool itself uses (`Nil`, `True`,
     `Default`, `Neutral`, a region code used as a name; the region at the
     end of a unit name never counts), or a single letter, so the tool cannot
     search for them elsewhere in the log. The log is refused rather than
     written unchecked; there is no override.
   - `other player's GUID without a unit name xN` (combat log, with
     `--pseudonymise-other-players` only): a GUID of another player appears
     N times, and not one of those times anywhere in the kept lines has their
     name in quotes right after it, so the tool has no invented name to tie
     it to. Usually `unmapped player GUID`
     is on the same line. If the GUID is one of yours, pass `--own-guid`;
     otherwise the log cannot be used.
   - `account GUID`, `guild GUID`, `community GUID`, `BattleTag`,
     `email address`, `someone else's name on an own realm`: the file holds
     a Battle.net account id (yours or someone else's) or other people. Choose a different addon's file. If your realm's name is
     also a lore word (a zone, a character's surname), this label can fire
     on game text such as `Zone:<realm>`; there is still no override, so
     choose another file, and expect a longer passed-over list.
   - `surviving identity string (…)`,
     `surviving short identity string (whole word or glued)`,
     `identity string not replaced whole`, `unblanked identity CVar`: one of
     your names survived in a casing or position the tool will not rewrite.
     Choose another file. If it is `Config.wtf` and the cause is a character
     or realm whose name (five letters or more) is part of a real CVar name
     (Sound, Camera, Target…), there is no override today: tell the
     conductor, and record the CVar name in the findings.
   - `surviving identity string (spaced or apostrophe spelling)`: the part
     after the hyphen in a `<First>-<Second>` folder appears in the file with
     a space, apostrophe or hyphen inside it, and the tool never saw that
     spelling in a folder. Pass the spelling as it appears in game as
     `--extra-name` and re-run.
   - `character list names a character this install has no folder for`
     (`character-list-order.txt` only): either the list includes an alt
     never played on this machine (pass that name as `--extra-name`), or its
     lines hold character GUIDs the tool does not know (pass `--own-guid`
     for each character). If every line is refused it is probably the
     second case. No Wave 1 module reads this file; leaving it out is fine.
   - `identity string inside a longer word xN`: one of your names sits
     glued inside a longer word (letters, digits or `_` on either side) in
     any file except addon files, `AddOns.txt` and edit-mode caches (their
     labels are below): a binding, macro or layout line naming an addon frame, a
     setting value, a creature or spell name in the combat log. The file is
     refused rather than rewritten, because a pseudonym inside a public name
     can be reversed. Choose another file, character or addon.
   - `identity string in combat-log game text xN` (combat log only): one
     of your names appears as a whole word somewhere other than the quoted
     unit name right after one of your own GUIDs: a creature, spell or NPC
     name, your pet's name, or your own unit name after a GUID the tool
     does not know is yours. Those names are public game data, so a
     pseudonym there could be looked up and reversed; the log is refused
     instead. If the same run also says `unmapped player GUID`, pass
     `--own-guid` for the character you logged with (on the Forever beta
     this is always needed) and re-run. Otherwise redo step 2 somewhere
     else, with any pet or summoned demon dismissed. Never edit the log.
   - `identity string inside a third-party addon file xN` (a `.toc` or any
     file under `Interface/AddOns/`): addon files are public, so any match of
     your names refuses the file. Pick another addon with `--toc`. Nothing
     forces an addon file through: `--extra-name` only adds names to look
     for, so it can only cause more refusals.
   - `identity string inside an addon name xN` (`AddOns.txt`): an installed
     addon's folder name contains one of your names. Leave that `AddOns.txt`
     out (choose another character) rather than capture it.
   - `identity string inside a length-prefixed layout name` (edit-mode
     caches): a layout you named carries one of your names. Rename the layout
     in game and recapture, or leave the file out.
   - `unreadable (…)`: see step 0.
   - `<path withheld>` with `in path: …` or
     `unsafe path component after scrubbing`: the problem is in the file's
     own path (a realm or character folder the scrub could not make safe).
     Nothing about that file is printed. Choose another character with
     `--character REALM/NAME` or `--character <First>-<Second>` (the real
     folder name; output paths show pseudonyms and `1` for the digits
     folder, so do not copy it from a `would write` line), or pass the name
     as `--extra-name` if it is
     one the folders did not reveal. `in path: identity string inside an
     addon's file name` is different: a SavedVariables file is named after an
     addon whose name contains one of yours; choose another file with `--sv`.
     `in path: identity string inside a third-party addon file` is similar:
     an addon's folder or TOC file name contains one of your names; pick
     another addon with `--toc`.
     `destination escapes --out` and
     `a second source file maps to this destination` are refusals of the
     output path, not of the content.
   - Lines in the passed-over list ending `no longer '…' once scrubbed` are
     not refusals: the file's interesting bytes were your name. Nothing to
     do.
   - With `--reuse-out`, every path listed under "were NOT written by this
     run" is a stale copy from an earlier run. Delete it by hand before
     moving anything.
   - `lab_capture: --character: no such character in this flavor` or
     `… the retail-style twin … could not be paired with a character` (exit
     2, nothing written): the first means no flavor has a character by that
     name (check the spelling and the `REALM/NAME` form); the second means
     you named a `<Realm>/<First>` folder the tool could not pair, so pass
     the real `<First>-<Second>` folder name instead. With several flavors
     installed, a character found in one flavor is captured there and each
     other flavor that has character folders prints
     `note     <flavor>: --character matched no character here; skipped`;
     that flavor's account-level files are still captured. `--flavor
     <folder>` limits the run to one flavor.
   - `note     <flavor>: the chosen character's retail-style twin could not
     be paired …`: the tool could not tell which `<Realm>/<First>/` folder
     belongs to the character (several candidates, or a contested one), so
     the character is captured without `AddOns.txt`. That is safe; pick
     another character if you want `AddOns.txt` in the corpus.
3. `look   CVars to review by eye: …`: open that config file and read those
   lines. If a value names you, a device ("…'s AirPods"), a path with your
   home folder, a realm or a long id, re-run with `--blank-cvar <name>` and
   list the name in the `docs/LAB_FORMATS.md` §5 amendment.
4. `look   Name-Realm-shaped string that is not a pseudonym pair` and
   `look   whisper/invite/target macro line or @Name`: open the reported
   line. Players on realms where you have no character are never refused;
   this note is all you get. Two more notes of the same kind:
   `own realm near an unexplained capitalised word` and
   `own realm next to an unexplained lowercase word` point at a word next to
   one of your realms, joined by a space, comma, tab or prose, or on the
   neighbouring line. Both are noisy: the capitalised one fires on every
   combat log line, the lowercase one on most structured SavedVariables
   files. Read the first reported line of each file; a real player's name
   there means swap the file. Another player's name means drop or swap the
   file (`--sv`). For macros, either accept that the name becomes public or
   delete that macro in game and recapture; read `macros-cache.txt` in full
   anyway, the note does not know every slash command.
5. `look   own realm next to a faction, region or 'Default' word`: expected in
   almost every Ace3, DataStore or auction addon file. Open the first few
   and check the segment *beyond* that word. (A player behind a region or
   `Default` word, `Jaina-US-<realm>`, is refused, not noted.)
6. `look   short identity string inside a longer word`: a name of yours under
   five letters sits inside a longer word and was left alone. Almost always
   coincidence (`max` inside `maximum`). Read the line once; if it really is
   your name glued to something, swap the file.
7. The "replacements per pseudonym" summary: a count in the hundreds means
   one of your names is also a game word, rewritten as a whole word. (A name
   glued inside a longer word now refuses the file instead, so a written
   file never shows an `embedded` count.) Run
   `grep -rniE 'lab(char|realm|name|account|other)|part[b-h]\b' lab/core/tests/fixtures/incoming/`
   and read the hits. CVar names are protected from rewriting and TOC files
   are refused on any match; whole-word matches in bind lines, macro bodies
   and Lua strings are still rewritten, so read those hits. In a combat log
   the only name rewrites are your own unit names after your own GUIDs and, with
   `--pseudonymise-other-players`, other players' GUIDs and unit names
   (`Labother…`, `Player-9998-…`); the log's provenance row then says
   `other-players-pseudonymised: N`, the number of other players in it.
   Every combat log, with or without that flag, also says
   `unit-guids-rewritten: N` (and its `wrote` line `N unit GUIDs rewritten`):
   the number of creature, pet, vehicle and object GUIDs whose server,
   instance, zone and spawn parts were replaced with invented ones
   (`Creature-0-1-0-2-<npc id>-0000000000`). The NPC or object id stays. A
   non-zero count is expected in any log that has a creature in it. If a log
   is `REFUSED` with `GUID-like token the tool cannot classify xN`, it holds a
   GUID-shaped token of a shape the tool does not know, or a GUID body with
   no type or with typographic dashes. Report the count; do not edit the log.
   Every combat log's row also says `timestamps-shifted`: its timestamps and
   the date in its file name were moved by that log's own offset. The
   captured log's name is therefore not the one in your `Logs/`.
   Pseudonyms are
   always ASCII, so
   `LC_ALL=C grep -rniE '(lab(char|realm|name|account|other)|part[b-h])[a-z]*[^ -~]' lab/core/tests/fixtures/incoming/`
   must print nothing (BSD and GNU grep both take this; a non-ASCII byte
   glued to a pseudonym means a name's tail survived the scrub).
8. Blanked `SET x ""` lines and the `Lab…` names are scrub artefacts. Do not
   record them as client behaviour in the findings table below. Refusal and
   `look` lines carry offsets or counts only, never text, and are safe to
   paste into the PR;
   `--show-map` output never is.

## Capture set (per flavor)

- `.build.info` (install root) and `<flavor>/.flavor.info`
- `WTF/Config.wtf`

## Review before committing

```bash
grep -rInE '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+|#[0-9]{4,}' lab/core/tests/fixtures/incoming || echo clean
grep -rIn "$USER" lab/core/tests/fixtures/incoming || echo clean
# PowerShell: Select-String -Path lab/core/tests/fixtures/incoming -Recurse -Pattern $env:USERNAME
```

The tool already refuses on emails and BattleTags; this is the human check.
A clean `gitleaks` run says nothing about identity: its rules look for
credentials. The repository is public, so read, in every file, for what no
tool can know:

- **Other players.** Friend and ignore lists, guild rosters, whisper and
  chat history, group members in damage-meter segments, auction sellers,
  mail and trade partners, `Name-Realm` strings on any realm. The tool
  refuses a name joined to one of *your* realms by `-`, ` - `, `.`, `|`,
  `:`, `/`, `_`, an en or em dash, parentheses, or any of those across a
  line break, and a name ending in a digit; it only *notes* a name joined
  by a space, comma, tab, `~` or prose. It cannot see separate `name` and
  `realm` fields of one record, or a name with no realm at all. Run
  `grep -rn 'Labrealm' lab/core/tests/fixtures/incoming` and read each line
  for a neighbouring real name. Prefer addons that store settings over
  addons that store people.
- **Names of groups.** Guild, community and custom chat channel names
  (`chat-cache.txt`), layout and profile names in the edit-mode file.
- **Macro bodies** (`macros-cache.txt`, and macro text stored inside
  SavedVariables), read in full. The tool notes the common name-taking
  commands (`/w`, `/invite`, `/target`, `/pr`, `/cw`, `/who`, `/kick`,
  `/inspect`, `[@Name]`, `/run` calling a whisper or invite function), but
  not every one.
- **GUID families the tool does not know.** It refuses `Player-` (unless
  yours), `BNetAccount-`, `Guild-` and `ClubFinder-`; those three spellings
  are reviewer memory. `Community-…` and anything else id-shaped passes.
  Record the real spellings you see in `docs/DATA_SOURCES.md`.
- **Every line of every `Config.wtf` and `config-cache.wtf`**, not only the
  ones the tool pointed at: device names, a path containing your home
  folder, a realm that is not yours, club ids, any long id-looking integer.
- **Bare numeric ids** (`bnetIDAccount`, presence ids, `clubId`, guild ids).
  They cannot be detected at the byte level.
- **Encoded or compressed addon blobs** (WeakAuras, Plater, Details,
  AceSerializer, LibDeflate strings). Nobody can inspect them; prefer not to
  capture a file that contains one.
- **Your names in forms the tool does not derive.** Locally, and never
  pasted anywhere: `grep -ri` for each real character and realm name, with
  and without spaces, in lowercase and slug form (`area-52`), with `_`, `.`
  or a curly apostrophe (`’`) between its words, and for names with
  diacritics in both composed and decomposed form. Also each part after the
  hyphen in a `<First>-<Second>` folder, spelled the same ways.
- **Reversal from context.** A realm pseudonym sitting next to a zone or NPC
  name can give the realm away (`"Labrealma, Netherstorm"`). Read the hits
  of the `Lab…` grep from "Reading the output".
- **`.build.info` on the Forever beta**: look at the `Armadillo`, key and
  `Last Activated` columns before committing it.
- TOC `## Author` and `## X-*` fields are third-party and already public
  for addons you downloaded. An addon you wrote carries your name or handle
  in `## Author:`. Pass that name as `--extra-name` (step 5) even when it is
  not a character name: the tool then refuses the file as a third-party
  addon file, and you pick another addon for the TOC slots. Without it, a
  handle no folder reveals is written unrefused.

Fixtures have their own `check-added-large-files` ceiling of 16 MB
(`.pre-commit-config.yaml`; everything else in the repository stays at
512 KB), so the multi-MB SavedVariables file this runbook asks for (waived 2026-09-22, see M10-03 in `docs/BACKLOG.md`) commits
without any exemption. The automatic selection never picks a file over
8 MiB (`--max-sv-bytes`); only a file you name with `--sv` can be larger. A
fixture is never trimmed or split to fit (L8): if a file you want is over
16 MB, leave it out, say so in the PR with its size, and pick a smaller one.
