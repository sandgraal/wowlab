# M0-04 — Schema and migrations

Written by the conductor on 2026-09-10, after M0-03 (PR #5) merged.

## Separation applies

`AGENTS.md` makes test-writer / implementer separation mandatory for
migrations, and the backlog has no `M0-04T` ticket. The conductor dispatches
`test-writer` first with the grader scope below, and the implementer starts
only after that `[TEST]` PR is merged. The graders, derived from plan §7 and
`.claude/rules/migrations.md`, not from any implementation:

- `alembic upgrade head` on an empty database, `downgrade base`, `upgrade
  head` again, all clean (the up/down/up proof as a test, not just a pasted
  transcript).
- After upgrade, inserting two `snapshots` rows with the same `content_hash`
  for the same character is rejected by the partial unique index.
- After upgrade, two `sim_jobs` rows with the same `(profile_hash,
  simc_version)` and `status = 'complete'` are rejected; the same pair with
  one row not complete is accepted.
- Every table in plan §7 exists after upgrade and none exists after
  downgrade.
- `game_items` / `game_spells` / `game_talents` are keyed by `game_version`.

## No Postgres on the conductor's machine

Docker and the Compose plugin are still absent here, so `make up` and
therefore step 4 of `/migration` cannot run locally. Two ways to get the
proof:

- CI's `API lint, typecheck, tests` job runs a `postgres:16` service with
  `DATABASE_URL=postgresql+psycopg://bronze:bronze@localhost:5432/bronze`
  (`.github/workflows/ci.yml`). Graders that need a database read that
  variable and skip cleanly when it is unset, so `make test` still passes on
  a machine without Postgres and the real proof comes from the CI log.
- The Makefile from M0-03 exports `DATABASE_URL` from the per-worktree port
  block; a developer with the stack up gets the same graders against it.

Paste the CI job's up/down/up output into the PR body as the acceptance
proof and say that it came from CI.

## `game_version` and the open ADR-0007 question

The ADR-0006 amendment of 2026-09-10 (PR #6) keeps `game_version` on the
`game_*` tables as the patch triple snapshots carry and moves the full
client build, hotfix date, and SimC commit SHA into an additive per-version
manifest. Whether a within-patch hotfix re-ingest becomes a composite key
`(game_version, build)` or a hotfix-date column is an owner decision that
gates M1-05, not M0-04. Ship §7 as written; the manifest and any key change
arrive as a later additive revision. Do not pre-empt the decision in the
initial migration.

## Health endpoint

`/health` is a liveness probe with no database dependency (M0-03 kept it
that way to avoid colliding with this ticket's driver dependencies). M0-04
adds SQLAlchemy and psycopg; a readiness check that pings the database is in
scope here if it stays additive to the existing `/health` contract that
`tests/test_health.py` and the compose healthcheck depend on.
