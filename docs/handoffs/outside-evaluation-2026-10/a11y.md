# Accessibility auditor (WCAG 2.2 AA, `wowlab ui` and the CLI)

## Verdict

For a sighted mouse user the browser view is in good shape. The text colours were picked with care, nothing animates, it reflows at 200% zoom, and axe-core reports only one moderate violation across ten tab and theme states. I would not yet recommend it to a keyboard-only or screen-reader user. The CLI is the opposite. It prints no colour, its output is line-based and labelled, it degrades safely when stdin is not a terminal, and every command has `--json`, so it is the accessible path today. Recommend the CLI to those users and say so in the docs. **The biggest problem is that the page fights screen readers and keyboard users at the moments that matter.** Toggling a folder drops keyboard focus to `<body>`. Two `aria-live` regions wrap whole panes and push thousands of characters of JSON into speech. The tree claims the ARIA `tree` role but has none of its keyboard behaviour. The Confirm that changes game files sits *before* the plan it confirms, has the bare name "Confirm", and the plan behind it is a collapsed JSON node. axe passes all of this; WCAG 2.2 AA does not: 2.4.3 (focus order), 4.1.2 (name, role, value), 4.1.3 (status messages), and 2.4.11/1.4.11 for the focus ring on the parchment pane. These are UI-layer fixes that touch no invariant.

## What works

- **Text contrast passes AA in both schemes.** I computed every token pair in `page.css`, composited the alpha backgrounds, and covered the fixed badge colours. The lowest body-text pair is 5.38:1 (light, gold on selected). Badge text runs 8.2 to 11.7:1. Gear quality names are bold 19.2px, so they count as large text, and the lowest is Epic at 3.94:1 (needs 3:1). Full table: `$EVAL/work/a11y/contrast.txt`.
- **Verdicts never rely on colour alone.** Every badge carries its label as text ("wowlab won't touch", "folder", "wowlab can edit"). In the tree it also carries a visually hidden ": <words>" for screen readers. A key disagreement says "disagrees" in text, and macro findings are sentences.
- **Every form control has a programmatic label** (`<label for>` or a wrapping label), and the tabs carry `aria-selected` and `aria-controls`. `lang="en"` is set and the iframe has a `title`.
- **No motion at all:** no CSS transition or animation, and `document.getAnimations()` returned 0. `prefers-reduced-motion` has nothing to act on, so it passes trivially.
- **Zoom and spacing hold up.** At 200% zoom (640 CSS px) and at 200% text-only size, no tab scrolls horizontally. The WCAG 1.4.12 text-spacing override clips nothing except the intentionally hidden `.unseen` spans.
- **The keyboard alone reaches every control and never gets trapped.** Plan, then Confirm, is two Tabs.
- **The strict hash-based CSP** blocked axe injection (I had to use `bypassCSP`). That is good for security and has no accessibility cost.
- **The CLI:** no ANSI codes anywhere (`cli.py` has no `secho` or `style`, and rich markup is off), so `NO_COLOR` is satisfied by construction. `char gear` gives quality in words ("Uncommon, item level 15"), where the UI uses colour. All 47 leaf commands accept `--json` (checked one by one). A prompt on non-TTY stdin reads EOF, prints "Nothing was changed." and exits 1.

## Findings

### F1 — Opening or closing a folder destroys the focused button; keyboard focus falls to `<body>`
- Severity: major
- Area: ui / Explorer tab (`page.js:374` `drawTree` → `tree.replaceChildren()`, called from `toggle`)
- Evidence: `node $EVAL/work/a11y/node/probe2.js "<url>" $EVAL/work/a11y/shots`. The log:
  `focused twisty: button.twisty "Close _classic_beta_"` / `after Enter: BODY` / `next Tab lands on: button.twisty "Close World of Warcraft"`. Every expand or collapse sends the user back to the top of the tree. The filter inputs (`input` event → `drawTree`) rebuild the tree the same way, but focus is in the input there, so it survives.
- Impact: a keyboard user exploring a folder deep in a real install (the AddOns folder alone can hold 100+ addons) has to Tab back down from the root after every toggle. A screen reader announces nothing and loses its place. This fails WCAG 2.4.3 in practice.
- Proposal: after a redraw, restore focus to the element with the same `data-path` and role (twisty or name). Better, adopt F3's roving tabindex, which makes this trivial. Add a Playwright-free unit test that runs `toggle` in jsdom, or a `tests/ui` check that a redraw keeps `document.activeElement.dataset.path`.
- Status: new

### F2 — Two whole panes are `aria-live`: selecting a file or running a command pushes the entire result into speech
- Severity: major
- Area: ui / Explorer detail pane (`page.html:44` `<aside id="explain" aria-live="polite">`), Commands detail (`page.html:65` `<section id="detail" aria-live="polite">`)
- Evidence: probe logs. Picking `.build.info` sets 602 characters of live-region text. Pressing **Preview** on `Config.wtf` makes the live region hold 8,170 characters. Running `cvar list` gives `section#detail (aria-live=polite) text length: 12667`. Picking a command also re-announces its whole help paragraph (about 700 characters for `snap restore`). The real status lines (`#status`, `#explain-status`) carry no `role="status"` of their own and are only announced because they sit inside these oversized regions.
- Impact: NVDA and JAWS read additions to a polite region in full. A screen-reader user hears minutes of JSON keys after every Run or Preview, and cannot get the one line that matters ("Plan, nothing was changed: exit code 0", "Confirmed: exit code 0", "Journaled as 00000001-…") without it. This fails WCAG 4.1.3, because the status is not distinguishable from content.
- Proposal: remove `aria-live` from `#explain` and `#detail`. Give `#status`, `#explain-status` and `#confirm-note` `role="status"`, and set them to one short sentence ("cvar list finished: 412 settings; result below", "Plan ready: 1 change. Confirm is below the plan"). Use `role="alert"` for refusals and non-zero exits. Put the rule in LAB_PLAN §14 (the UI section): "a live region holds one sentence, never a result".
- Status: new

### F3 — `role="tree"` and `treeitem` without the tree keyboard model; treeitem names are polluted
- Severity: major
- Area: ui / Explorer tab (`page.html:42`, `page.js:323-370`)
- Evidence: `ArrowDown` on the first tree name leaves focus where it was ("after ArrowDown on first tree name: button.name.folder "World of Warcraft/""). Every folder row is two tab stops (twisty and name) and every file is one, so reaching the detail pane from `.build.info` took 20 Tabs in a 49-path sandbox. The accessible names from the Chromium AX tree (CDP `Accessibility.getFullAXTree`) are
  `treeitem: name="Close World of Warcraft World of Warcraft/"` and
  `treeitem: name="Close _classic_beta_ _classic_beta_/ folder : —; a folder, see the files in it flavor folder"`.
  The twisty's action label leaks into the item's name, and the em dash is read as "dash" or skipped. `aria-selected` sits on the `li`, while focus sits on an inner button.
- Impact: screen readers switch to focus mode on a `tree` and tell the user to use the arrow keys, which do nothing here. This fails WCAG 4.1.2 because the role promises behaviour that is absent. Tab cost grows with every open folder, and on a real install the explain pane is effectively hundreds of Tabs away.
- Proposal: either (a) implement the WAI-ARIA APG tree view: one tab stop, Up/Down/Left/Right/Home/End, `aria-expanded` on the focused treeitem, Enter to select, `aria-label` on each treeitem = "name, verdict words". Or (b), the cheaper fix, drop `role=tree`/`treeitem`/`group`, keep plain nested `<ul>` of buttons, and put `aria-expanded` on the twisty. Either way, add a "Skip to details" link, or move focus to `#explain-title` (`tabindex=-1`) after a selection.
- Status: new

### F4 — The Confirm that changes game files comes before its plan, is named only "Confirm", and the plan is a collapsed JSON node
- Severity: major
- Area: ui / Commands tab, confirm flow (`page.html:71-75`: `#confirm-box` precedes `#result-tree`; `ui/__init__.py` `_Offer` gives `snap restore` no note)
- Evidence: `$EVAL/work/a11y/shots/restore-plan-dark.png`. I ran `snap restore <id>` against a sandbox where `WTF/Config.wtf` had changed. The page shows "Plan, nothing was changed: exit code 0", then the **Confirm** button, then the JSON tree with `"plan": [1]` collapsed. `confirm-note` is empty and `stderr` is empty. The only human-readable statement of the change ("replace WTF/Config.wtf (3,755 bytes)") exists in the CLI's text mode and never reaches the page. By keyboard, "Tab after plan lands on: button#confirm". The Confirm comes before the plan in DOM order, and it has no `aria-describedby`.
- Impact: a screen-reader or cognitive-load user reaches the button that rewrites their install before they meet what it will rewrite, and must expand a JSON array to find out. WCAG 3.3.4 is formally met, because the change is reversible with `undo`. It fails the spirit of 2.4.6 and 3.3.2, and it undercuts the README's promise that the view runs a change "only when you confirm the plan it shows".
- Proposal: render the plan as a plain list (action, path, size) above Confirm, generated from the report's `plan` array, or show the CLI's stderr plan as the CLI prints it. Put Confirm after that list in DOM order. Give it a specific name ("Confirm: restore 1 file from snapshot 20261021T…"), or point `aria-describedby` at the plan summary. After a plan, move focus to the plan heading. After Confirm, move focus to the "Journaled as …; `wowlab undo` reverses it" note.
- Status: new (M14-02/M14-03 built the mechanism; neither covers presentation)

### F5 — Focus ring is invisible on the parchment pane in the dark (default) scheme
- Severity: major
- Area: ui / Explorer detail pane (`page.css:64` `:focus-visible { outline: 2px solid var(--gold) }`, never overridden for `.parchment`)
- Evidence: `python3 $EVAL/work/a11y/contrast.py`. Gold `#e3bb55` against the parchment is 1.20:1 on `#e4d0a2`, 1.48:1 on `#f3e7c9`, 1.50:1 on the Copy button's background and 1.40:1 on the hint box. The light scheme's `#6f4f0c` gets 4.9 to 6.2:1. Screenshots at 3x: `shots/focus-copy-dark-x3.png` (a pale ring hard to tell from the button's own border) and `shots/focus-copy-light-x3.png` (clear).
- Impact: a keyboard user cannot see which Copy or Preview button has focus in the pane where every action lives, in the scheme most players get by default. This fails WCAG 2.4.7 in effect and 1.4.11 (focus indicator under 3:1), and 2.4.13 is the AAA target.
- Proposal: `.parchment :focus-visible { outline-color: var(--ink); }` (`#2a1c0c`, about 10:1), or a two-tone ring (`outline` plus a `box-shadow` in the other colour). Add the pair to a contrast unit test that parses `page.css`, like `contrast.py`, so a palette change cannot regress it.
- Status: new (the M13 UI ticket's "body text meets WCAG AA" covered text only)

### F6 — Reflow fails at 320 CSS px (400% zoom): the tabs and the Commands panes do not wrap
- Severity: major
- Area: ui / banner `.tabs` (`page.css:77`), `.commands-body` (`page.css:178-179`)
- Evidence: `probe.js`, reflow section: `400% (1.4.10 reflow, 320 CSS px): scrollWidth=483 clientWidth=320 hscroll=true`. On Commands, `detailW=40`, and `z320.js` measures the first input at 16px wide. Screenshot `shots/zoom-320-commands-body.png`: the command list keeps `min-width: 14rem`, and the form is squeezed into a 40px column with one word per line. At 640px (200%) there is no horizontal scroll.
- Impact: a low-vision player at 300 to 400% zoom, or anyone with the view in a narrow side-by-side window, cannot use the Commands tab, including Confirm. Fails WCAG 1.4.10.
- Proposal: add `flex-wrap: wrap` to `.tabs`, and `@media (max-width: 40rem) { .commands-body { flex-direction: column } #commands { min-width: 0; max-height: 40vh } }`. Add a 320px Playwright or `--screenshot` smoke check to `make ui-check`, or to the owner's end-to-end list in the UI ticket.
- Status: new

### F7 — Picking a command leaves focus in a 47-button list; the buttons are toggle buttons; the form's help is not linked to its inputs
- Severity: minor
- Area: ui / Commands tab (`page.js:2031` `pick`, `page.js:1966-1990` `field`)
- Evidence: the probe log reads "Tab presses from 'snap gc' to Run: 21". For `snap restore`, the field labels are `snapshot_id | --paths | --root`, the raw CLI parameter names (`/api/commands` gives `sv merge` the labels `file`, `--into`, `--from`, `--base`). Each input has `no-describedby`, so its `<small>` help is not announced. Commands use `aria-pressed`, so a screen reader says "snap gc, toggle button, pressed". Running `snap restore` with an empty ID gives "Plan, nothing was changed: exit code 2", with Click's "Missing argument 'ID'" only in `#stderr`. The page sets no `aria-invalid` and moves no focus, although the input is `required`.
- Impact: keyboard users pay up to 46 Tabs to reach a form. Screen-reader users hear "dash dash into, edit text" for the field that names the target of an `sv merge` write, with no help text.
- Proposal: after `pick`, focus `#title` (`tabindex=-1`). Use `aria-current="true"` or a single-select listbox instead of `aria-pressed`. Give each input `aria-describedby` pointing at its help. Let the server send a human label ("Target file (--into)"). Validate `required` fields before a run, and set `aria-invalid` with a message.
- Status: new

### F8 — Information only in `title` tooltips or in colour, out of reach for keyboard and colour-blind users
- Severity: minor
- Area: ui / Character tab (gear names), Commands list, Keys table
- Evidence: in `shots/gear-dark.png`, item quality appears visually only as the name's colour (green Uncommon, white Common, grey Poor). The word is in a visually hidden span and in `title`, and `title` never shows on keyboard focus. The disabled `ui` command explains itself only in `title` ("Not offered in this version: the UI itself"), and a disabled button cannot take focus. On the key table, `row.page_note` and shared notes appear only in `title` (`page.js:1669`, `1685`).
- Impact: a colour-blind sighted player cannot tell a Rare from an Epic in the Character tab, and the CLI prints the word. Keyboard users never see any tooltip-only fact. This fails WCAG 1.4.1 for the gear quality.
- Proposal: show the quality word visibly, small and muted after the name ("Flax Belt · Common"), as `char gear` does. Render the disabled-command reason as text under the list. Show page notes inline, or behind a disclosure button.
- Status: new

### F9 — Forced-colours (Windows High Contrast) mode hides the selected tree row and the picked command
- Severity: minor
- Area: ui / Explorer tree, Commands list
- Evidence: `node $EVAL/work/a11y/node/forced.js "<url>" $EVAL/work/a11y/shots` emulates `forced-colors: active`. In `shots/forced-explorer.png`, `.build.info` is selected but looks like every other row, because selection is a background plus an inset `box-shadow` and forced colours removes both. In `shots/forced-commands.png` every command button gets the same system border, so the picked one cannot be told apart.
- Impact: Windows High Contrast users, a real share of low-vision Windows players, lose track of the selection.
- Proposal: add `@media (forced-colors: active) { .row.selected, #commands button[aria-pressed=true], .tab[aria-selected=true] { outline: 2px solid Highlight; forced-color-adjust: none } }` or similar, and a visible text marker for the selected row.
- Status: new

### F10 — Heading hierarchy skips a level on the Gaps tab (the only axe violation)
- Severity: minor
- Area: ui / Gaps tab
- Evidence: axe-core 4.10.2, tags wcag2a/aa, wcag21a/aa, wcag22aa and best-practice, run on 10 states (5 tabs × dark/light; logs in `$EVAL/work/a11y/shots/probe.log`). Every state reports 0 violations except Gaps: `heading-order (moderate) x1: .gap-section:nth-child(1) > h3`. The tab has H1 then H3 "Paths with no file-map row" and H3 "Not entered", with no H2. axe marks `color-contrast` "incomplete" (37 to 93 nodes) because the page uses gradient backgrounds. The manual token computation in F5 and *What works* stands in for it.
- Impact: screen-reader users who move by heading get an unexpected level. It is small, but it is the only machine-detectable issue, so it is a cheap win.
- Proposal: give each tab panel an H2 (visually hidden if need be: "Gaps", "Commands", "Character"), so each panel's headings start at H2. Add axe-core, vendored under ADR-0034's single-library rule or as a test-only npm dependency, to a CI smoke test.
- Status: new

### F11 — Status changes that are never announced, and a Copy error that vanishes after 2 seconds
- Severity: minor
- Area: ui / Copy buttons (`page.js:557`), tab switching
- Evidence: Copy swaps its own text to "Copied", or to "Copy did not work in this browser; use Copy in another browser", then back after `setTimeout(…, 2000)`. That text sits in no live region (it is inside the oversized `#explain` live region from F2, which is the wrong reason to be announced). Gaps and Character load on tab switch, and their `role="status"` paragraphs are empty during the load.
- Impact: a screen-reader user cannot tell whether a copy worked, and a slow reader loses the failure message after 2 s (WCAG 2.2.1 in spirit).
- Proposal: one shared `role="status"` element for the page that receives "Copied the command" or "Copy failed: …". Do not revert the failure text on a timer.
- Status: new

### F12 — The colour scheme follows the OS only; there is no in-page choice
- Severity: idea
- Area: ui / theme (`page.css` `@media (prefers-color-scheme: light)`)
- Evidence: no toggle and no `data-theme` hook. The parchment pane stays light in both schemes, and the gear table stays dark in both. That is by design (BACKLOG M13 UI ticket: "a light scheme follows `prefers-color-scheme`").
- Impact: a player who keeps the OS dark but needs light text-on-dark reversed for one app (astigmatism, glare) cannot switch, and a dark-mode user still gets a bright parchment pane beside dark panels.
- Proposal: a two-state theme switch, kept in `localStorage`, with `:root[data-theme]` overrides. It needs no network and no new language.
- Status: new

### F13 — CLI text that reads badly aloud: inline `[verify]` markers, a bare em dash as a value, truncated command help
- Severity: minor
- Area: cli / `binds list`, `tree --explain`, `wowlab --help`
- Evidence: `wowlab binds list` ends with "…uses its own file instead [verify]. The server can replace…". `wowlab tree --explain` prints `edit: —; a folder, see the files in it`. `wowlab --help` cuts summaries to one line ("Characters as the lab-addon recorded them in WowLab.lua (read..."), even with `COLUMNS=200`.
- Impact: a screen reader says "left bracket verify right bracket", an internal doc marker, to players, and reads the em dash as "dash" or silence where the value should be. Truncated help hides the read-only/writes distinction ("(read..." for `char`).
- Proposal: map `[verify]` to plain words in user output ("(not yet confirmed)"), and print `edit: not applicable (a folder)`. Give each group a short summary that fits Click's line, or set `short_help`.
- Status: new

### F14 — `wowlab ui --help` says the opposite of what the UI does
- Severity: minor
- Area: cli / `ui --help` (`cli.py:9900`)
- Evidence: `wowlab ui --help` says "Commands that change your game files, and the other commands that take --yes, are not offered in this version." The UI offers `snap restore`, `undo`, `profile apply`, `sv merge` and `addon install|remove` behind Confirm. I ran a confirmed `snap restore` from the page: "Confirmed: exit code 0 … Journaled as 00000001-4cb982e2". The README describes the confirm step.
- Impact: CLI help is the first and most accessible document for a screen-reader user, and here it understates what the page can change in their install.
- Proposal: update the docstring to the README's wording (M14-02/03 shipped the behaviour), and add a test that the `ui` help names the confirm step.
- Status: new

### F15 — `--json` is the accessible path but fails as text, and the docs never say it is the accessible path
- Severity: idea
- Area: cli / errors under `--json`; README/INSTALL
- Evidence: `wowlab snap show nope --json` prints `wowlab: not a snapshot id or prefix: 'nope'` on stderr, with empty stdout and exit 1. `sv dump --json nope.lua` prints a raw `[Errno 2]` string. Neither README nor INSTALL mentions screen readers, keyboard use or `--json` as an alternative to the browser view.
- Impact: a blind player who pipes `--json` into a reader or `jq` gets nothing parseable on failure, and nobody tells them that the CLI is the better route today.
- Proposal: under `--json`, emit `{"error": {"code": …, "message": …}}` on stdout with the same exit code. Add a short "Using wowlab with a screen reader or keyboard only" section to the wiki, pointing to the CLI and `--json` until F1 to F5 land.
- Status: new

## Top 3 changes

1. **Fix focus and announcements** (F1, F2): keep focus across tree redraws, and replace the two pane-sized `aria-live` regions with one-sentence `role=status`/`alert` messages. This is a small JS change with the largest effect on keyboard and screen-reader users.
2. **Make Confirm understandable** (F4): a plain-language plan list above a Confirm whose accessible name says what it does, with focus moved to the plan and then to the journal note. This is the one place the UI writes into the install. Also fix the dark-scheme focus ring on the parchment pane (F5), a one-line CSS change.
3. **Honour the roles the page declares, or drop them** (F3, F6): either a real APG tree or plain lists, and a 320px reflow for the tabs and Commands. Lock the gains in with an automated a11y smoke test (axe-core plus a token contrast check plus a focus-after-toggle check) in `make ci`. The UI ticket's acceptance list only asks for text contrast.

## Not tested

- **Real assistive technology** (NVDA, JAWS, VoiceOver, Orca): none is available headless on this Linux box. Screen-reader effects are inferred from the Chromium accessibility tree (CDP) and live-region content lengths, not heard.
- **The Looks tab's embedded page:** `looks page` needs cached game tables (db2), and the network was off-limits. Only the frame's `title` and sandbox were checked, not its content.
- **A real install's tree size:** the sandbox has 49 paths. Tab-stop costs on a real install (hundreds of addons) were extrapolated (2 stops per open folder, 1 per file).
- **Windows-specific behaviour** (High Contrast themes beyond Chromium's `forced-colors` emulation, Narrator) and macOS VoiceOver rotor behaviour.
- **Pointer target size** (WCAG 2.5.8): not measured systematically. The 1.3rem twisties (about 21px) look above the 24px spacing exemption, but this is unverified.

Then run `cd $EVAL/work/a11y/node && node probe.js "$(cat ../url.txt)" ../shots` (plus `probe2.js`, `forced.js`, `z320.js`, `spacing.js`, `focusshot.js`). Contrast: `python3 $EVAL/work/a11y/contrast.py`.
